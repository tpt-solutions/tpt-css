# tpt-css Design Specification

**Status:** Draft 0.1
**License:** MIT OR Apache-2.0 (dual, at the user's option)
**Implementation language:** Rust
**Core dependency policy:** zero third-party crates in the CSS core
**Provenance policy:** clean-room, spec-first; no porting or wrapping existing CSS engines
**Target modes:** AppFront-native and Web/DOM-compatible through adapters

---

## 1. Purpose

`tpt-css` is a new, clean-room CSS engine written in Rust.

It is responsible for:

```text
CSS text
  -> tokens
  -> stylesheet AST
  -> selector matching
  -> cascade
  -> specified values
  -> variable substitution
  -> property parsing
  -> computed styles
```

It is **not** responsible for layout, paint, HTML parsing, DOM implementation, JavaScript, networking, font loading, or animation timing.

The engine must be usable by both:

1. **AppFront-native documents**, where AppFront provides the tree and state model.
2. **Web documents**, where a future `tpt-dom` adapter provides DOM semantics.

The CSS core must not depend on either frontend.

---

## 2. Goals

### 2.1 Primary goals

1. **Clean-room implementation**
   - Implement from public CSS specifications.
   - Do not port, wrap, translate, or copy code from LibWeb, Servo, Blink, Gecko, WebKit, or other engines.
   - Do not depend on `cssparser`, `selectors`, `stylo`, `lightningcss`, or similar existing CSS implementation crates.

2. **Strict license purity**
   - All first-party code is dual licensed `MIT OR Apache-2.0`, copyright TPT Solutions.
   - The core crate has no third-party dependencies.
   - Optional integration crates may only depend on approved tpt crates usable under MIT.
   - No MPL, GPL, LGPL, Apache-only, or proprietary dependencies or code in the engine.
   - Any allowed dependency must offer MIT as a license option (`MIT` or `MIT OR Apache-2.0`).

3. **Pure Rust**
   - No C/C++ CSS engine dependency.
   - No FFI in the core.
   - Core should compile as `no_std + alloc` where practical.

4. **Document-agnostic**
   - The engine styles an abstract tree.
   - AppFront and DOM are adapters, not core assumptions.

5. **Spec-traceable**
   - Every major algorithm should cite the relevant spec section.
   - Every supported property/selector/cascade behavior should have tests.
   - The engine should maintain a spec-to-test traceability matrix.

6. **Deterministic**
   - Cascade order must be stable.
   - Serialization must be deterministic.
   - No random hash iteration may affect style resolution.

7. **Safe against hostile CSS**
   - Malformed CSS must not panic.
   - Deep nesting, huge token streams, selector complexity, and variable cycles must be bounded.

8. **Incremental**
   - The engine must support invalidation and restyling without recomputing the entire document for every change.

---

## 3. Non-goals

`tpt-css` does not implement:

- HTML parsing.
- DOM node semantics.
- DOM events.
- JavaScript bindings.
- Layout.
- Paint.
- Compositing.
- Font loading.
- Image decoding.
- Network fetching.
- `@import` fetching.
- Animation timing drivers.
- Transition timing drivers.
- Used-value layout resolution.
- Browser UI.
- Devtools UI.

It may provide metadata needed by those systems, but it does not own them.

## 4. Design principles

### 4.1 Spec-first, not engine-first

Implementation order:

```text
spec section
  -> own algorithm description
  -> own Rust implementation
  -> own MIT tests
  -> external conformance oracle
```

Do not read another engine's implementation to decide how to implement a feature.

External test suites may be used as black-box oracles, but if strict MIT-only distribution is required, their source/assets must not be vendored into the MIT tree unless explicitly approved.

### 4.2 Separate syntax, semantics, and style resolution

The engine must keep these layers distinct:

```text
syntax      -> tokens and component values
parse       -> rules, declarations, selectors
selectors   -> matching and specificity
cascade     -> precedence and declaration selection
values      -> grammar parsing and computation
properties  -> property metadata
style       -> tree resolution, inheritance, invalidation
cssom       -> optional web-facing mutation APIs
```

### 4.3 No DOM leakage

The core must not contain HTML-specific assumptions such as:

- `div`
- `span`
- `href`
- `checked`
- `disabled`
- HTML case-insensitivity rules

unless those are supplied through the tree adapter or a web-specific profile.

The core may understand generic concepts:

- element name
- namespace
- attributes
- states
- parent/child/sibling relationships
- scope boundaries
- shadow boundaries
- inline style
- pseudo-elements

### 4.4 Computed style is not layout

`tpt-css` produces computed styles.

Layout-dependent values may remain unresolved or partially resolved until the layout engine consumes them.

Examples:

```text
width: 50%
height: auto
margin: auto
flex-basis: auto
grid-template-columns: 1fr 2fr
```

The CSS engine should not pretend to know used layout values unless the relevant context is explicitly provided.

## 5. Target profiles

### 5.1 AppFront profile

The AppFront profile is the first practical target.

```text
AppFront tree
  -> StyleTree adapter
  -> tpt-css
  -> computed styles
  -> tpt-layout
  -> tpt-paint
```

AppFront may provide:

- native component tree
- reactive state changes
- component scopes
- custom states
- direct Rust APIs
- optional JS/WASM scripting through tpt runtimes

The CSS engine must still be tested against web-oriented selector and cascade behavior so AppFront shortcuts do not corrupt the core.

### 5.2 Web profile

The Web profile is the long-term compatibility target.

```text
HTML
  -> tpt-dom
  -> StyleTree adapter
  -> tpt-css
  -> computed styles
  -> tpt-layout
  -> tpt-paint
```

The Web profile requires:

- DOM adapter
- HTML UA stylesheet
- CSSOM APIs
- web state semantics
- shadow DOM semantics
- visited-link privacy behavior
- web-compatible serialization
- web-compatible error recovery

The CSS core should remain the same.

## 8. Public API sketch

### 8.1 Parsing

```rust
pub struct ParseOptions {
    pub origin: Origin,
    pub quirks: QuirksMode,
```

## 9. Core tree contract

The CSS engine must depend on a small abstract tree contract.

```rust
pub type NodeId = GenerationalId;

pub trait StyleTree {
    fn root(&self) -> NodeId;

    fn parent(&self, node: NodeId) -> Option<NodeId>;
    fn children(&self, node: NodeId) -> &[NodeId];

    fn kind(&self, node: NodeId) -> NodeKind;

    fn name(&self, node: NodeId) -> QualifiedName;
    fn namespace(&self, node: NodeId) -> NamespaceId;

    fn attributes(&self, node: NodeId) -> &Attributes;
    fn state(&self, node: NodeId) -> ElementState;

    fn inline_style(&self, node: NodeId) -> Option<&DeclarationBlock>;

    fn scope(&self, node: NodeId) -> ScopeInfo;
    fn shadow(&self, node: NodeId) -> ShadowInfo;

    fn language(&self, node: NodeId) -> Option<&str>;
    fn direction(&self, node: NodeId) -> Option<Direction>;
}
```

The exact API may use iterators instead of slices if needed, but the contract must remain small.

```rust
pub enum NodeKind {

    Comment,
    Document,
    Fragment,
```

Only element-like nodes participate in selector matching.

Pseudo-elements may be represented as generated style nodes.

## 10. Syntax layer

### 10.1 Tokenizer

Implement CSS Syntax Level 3 tokenization.

Token kinds must include:

```text
ident
function
at-keyword
hash
string
bad-string
url
bad-url
delim
number
percentage
dimension
whitespace
CDO
CDC
colon
semicolon
comma
left-square
right-square
left-paren
right-paren
left-curly
right-curly
EOF
```

The tokenizer must:

- handle Unicode input correctly
- handle escapes
- handle newline normalization
- handle bad strings and bad URLs
- preserve source spans
- avoid panics on malformed input
- support bounded input length
- support optional comment preservation for tooling

Comments are ignored by default for style resolution.

### 10.2 Component values

Implement component value parsing:

```text
component value
  -> preserved token
  -> function
  -> simple block
```

Simple blocks:

```text
()
[]
{}
```

Component values are needed for:

- declaration values
- custom property values
- `var()` fallbacks
- unknown properties
- `@supports`
- `@media`
- selector arguments
- future property grammars

The component value layer must not eagerly interpret every value as a known property.

### 10.3 Source spans

Every meaningful AST node should carry a span:

```rust
pub struct Span {
    pub source: SourceId,
    pub start: u32,
    pub end: u32,
}
```

Spans are required for:

- diagnostics
- CSSOM mutation
- devtools integration
- conformance debugging
- spec traceability

### 12.3 Specificity

Specificity must be represented explicitly:

```rust
pub struct Specificity {
    pub a: u32,
    pub b: u32,
    pub c: u32,
}
```

Rules:

- ID selectors contribute to `a`.
- Class, attribute, and pseudo-class selectors contribute to `b`.
- Type and pseudo-element selectors contribute to `c`.
- Universal selector contributes nothing.
- `:where()` contributes nothing.
- `:is()`, `:not()`, and `:has()` use the most specific argument.
- `:nth-child(An+B of S)` includes the specificity of `S`.
- Nesting selector specificity must follow the nesting spec.

Specificity must be computed at parse time where possible.

### 12.4 Matching strategy

Default matching should be right-to-left.

For each selector:

```text
match rightmost compound against candidate element
walk combinators leftward
validate ancestor/sibling/scope constraints
return match result
```

Performance features:

- candidate filtering by id/class/type
- ancestor bloom filters
- sibling caches
- nth-child caches
- selector dependency tracking
- `:has()` invalidation graph

Matching must be deterministic.

### 12.5 Pseudo-elements

Pseudo-elements should be modeled as generated style nodes.

```rust
pub enum PseudoElement {
    Before,
    After,
    Marker,
    Placeholder,
    Selection,
    Backdrop,
    FileSelectorButton,
    Part(Atom),
    Slotted,
    Highlight(Atom),
    Unknown(Atom),
}
```

The CSS engine computes pseudo-element styles.

Layout/paint decide whether boxes are generated.

`::before` and `::after` require `content` support before they become useful to layout.

## 13. Cascade

### 13.1 Cascade inputs

The cascade receives:

```text
matched declarations
inline declarations
UA declarations
user declarations
author declarations
animation declarations
transition declarations
layer order
scope information
shadow context
specificity
source order
importance
```

### 13.2 Origins

```rust
pub enum Origin {
    UserAgent,
    User,
    Author,
    Animation,
    Transition,
}
```

Importance is separate:

```rust
pub struct Importance(pub bool);
```

The cascade must implement the CSS Cascade origin/importance ordering exactly.

High-level precedence:

```text
transitions
important user-agent
important user
important author
animations
normal author
normal user
normal user-agent
```

The implementation must cite the cascade spec and be covered by golden tests.

### 13.3 Cascade key

Each matched declaration should produce a cascade key:

```rust
pub struct CascadeKey {
    pub origin: Origin,
    pub important: bool,
    pub context: CascadeContext,
    pub inline: bool,
    pub layer: LayerOrder,
    pub scope_proximity: ScopeProximity,
    pub specificity: Specificity,
    pub order: DeclarationOrder,
}
```

The exact comparison order must follow the implemented cascade level.

The engine should initially target Cascade 5 behavior, then add Cascade 6 scoping proximity when `@scope` is enabled.

### 13.4 Layers

Support:

```css
@layer reset, base, theme;

@layer base {
  p { margin: 0; }
}

@layer theme {
  p { color: red; }
}
```

Rules:

- Layer order is established by first declaration.
- Normal declarations in later layers win over earlier layers.
- Normal unlayered declarations win over normal layered declarations.
- Important declarations in earlier layers win over later layers.
- Important layered declarations win over important unlayered declarations.

This behavior must be tested heavily.

### 13.5 Inline style

Inline style from the tree adapter must enter the cascade according to the spec.

The CSS engine must not treat inline style as a magical global override. It must participate in origin/importance/layer/specificity/order rules correctly.

### 13.6 Shorthand expansion

Shorthands must expand to longhands for cascade purposes.

Example:

```css
margin: 1px 2px;
```

expands to:

```text
margin-top: 1px
margin-right: 2px
margin-bottom: 1px
margin-left: 2px
```

The original shorthand should remain available for CSSOM serialization.

Cascade precedence belongs to the expanded longhand declarations.

### 13.7 Custom properties

Custom properties cascade like ordinary properties, but their values are token streams until substitution.

Algorithm:

```text
1. Cascade custom property declarations.
2. Build var() dependency graph.
3. Detect cycles.
4. Mark cyclic custom properties invalid at computed-value time.
5. Substitute var() references recursively.
6. Use fallbacks when a custom property is invalid or missing.
7. Parse resulting token streams against property grammars.
8. Mark properties invalid at computed-value time when substitution fails.
9. Compute registered custom properties according to @property.
```

Custom property names are case-sensitive.

Ordinary property names are ASCII case-insensitive in the default profile.

### 13.8 `initial`, `inherit`, `unset`, `revert`, `revert-layer`

Support CSS-wide keywords:

```text
initial
inherit
unset
revert
revert-layer
```

Behavior must be property-aware:

- inherited properties differ from non-inherited properties
- `unset` depends on inheritance
- `revert` depends on origin
- `revert-layer` depends on layer order

`all` must be supported as a shorthand-like CSS-wide property.

## 16. Style resolution

### 16.1 Resolution pipeline

For each element-like node:

```text
1. Collect matching rules.
2. Collect inline declarations.
3. Expand shorthands.
4. Cascade longhand declarations.
5. Cascade custom properties.
6. Resolve custom property cycles.
7. Substitute var() into longhand values.
8. Parse property grammars.
9. Apply CSS-wide keywords.
10. Compute values.
11. Inherit inherited properties.
12. Compute pseudo-element styles.
13. Store computed style.
14. Record invalidation dependencies.
```

Font-size computation must be ordered carefully because many relative values depend on it.

### 16.2 Environment

```rust
pub struct Environment {
    pub viewport: ViewportInfo,
    pub root_font: FontContext,
    pub media: MediaQueryEnvironment,
    pub containers: ContainerQueryContext,
    pub fonts: FontMetricsProvider,
    pub urls: UrlResolver,
    pub preferences: UserPreferences,
    pub env_variables: EnvVariables,
}
```

Not all providers are required in M0.

The engine must have sensible fallbacks or explicit unsupported diagnostics when a provider is missing.

### 16.3 Media queries

Support:

```text

aspect-ratio
```

### 16.4 Supports queries

```css
@supports font-tech(...) { ... }

```

Do not hardcode browser-like support strings.

### 16.5 Container queries

Container queries require layout context.

The CSS engine should define a provider:

```rust

    fn container_size(&self, node: NodeId) -> Option<ContainerSize>;

```

Container query evaluation may require style/layout interleaving.

M0 may disable container queries.

M2/M3 should support size containers with explicit integration into `tpt-layout`.

## 19. Error handling and limits

### 19.1 No panics on hostile input

The core must not panic on:

- malformed tokens
- unclosed blocks
- invalid selectors
- invalid declarations
- huge numbers
- deep nesting
- invalid UTF-8 boundaries after input conversion
- cyclic custom properties
- recursive `var()` fallbacks
- extremely long selector lists

### 19.2 Limits

```rust
pub struct ParseLimits {
    pub max_input_bytes: usize,

    pub max_rules_per_sheet: usize,
    pub max_var_depth: usize,
    pub max_calc_depth: usize,
}
```

Limits should be configurable.

When a limit is exceeded, the engine should produce a diagnostic and recover safely.

## 20. Security and privacy

### 20.1 No network in core

The CSS core must not fetch URLs.

`@import` and `url()` resolution should be delegated:

```rust
pub trait UrlResolver {
    fn resolve(&self, base: Option<&Url>, value: &str) -> ResolvedUrl;
}
```

The host decides whether loading is allowed.

### 20.2 Visited-link privacy

In Web mode, `:visited` must not leak history through arbitrary computed-style queries.

The engine should support a visited-style policy:

```rust
pub struct VisitedPolicy {
    pub allowed_properties: PropertySet,
    pub computed_style_lies: bool,
}
```

AppFront mode may disable visited semantics entirely.

### 20.3 Resource exhaustion

CSS is untrusted input.

The engine must bound:

- token count
- nesting depth
- selector matching work
- variable substitution depth
- calc depth
- stylesheet count
- rule count
- custom property graph size

### 20.4 No secret-dependent behavior

The core should not introduce timing or behavior differences based on private host data unless explicitly modeled by a privacy policy.

## 21. Performance requirements

### 21.1 Initial performance targets

M0 should be able to:

- tokenize at least hundreds of thousands of tokens per second on a normal desktop CPU
- parse medium stylesheets without excessive allocation
- resolve static trees with thousands of nodes
- avoid quadratic selector matching in common cases

These are engineering targets, not marketing claims.

### 21.2 Allocation strategy

Use:

- arenas for AST nodes
- atom interning for identifiers
- compact property IDs
- generational node IDs
- reusable style arenas
- cached selector matching results where safe

Avoid:

- string cloning in hot paths
- random hash iteration affecting cascade
- recursive descent without depth limits
- per-node heap allocation for every property

### 21.3 Determinism

Cascade order must not depend on:

- hash map iteration order
- pointer addresses
- thread scheduling
- random seeds

If parallelism is added later, it must preserve deterministic cascade results.

## 25. Open design questions

These should be resolved before or during M0/M1:

1. **Numeric representation**
   - Start with `f64`, or implement a decimal/rational CSS number type immediately?

2. **Atom interning**
   - Build a custom deterministic interner, or use an approved tpt primitive?

3. **Tree contract ownership**
   - Should `StyleTree` return slices, iterators, or arena-backed handles?

4. **Pseudo-element representation**
   - Generated nodes inside the style tree, or side tables keyed by node + pseudo?

5. **Font metrics provider**
   - How much font-relative computation belongs in CSS versus layout/font systems?

6. **Container query integration**
   - How will style resolution request container sizes without creating layout cycles?

7. **Animation boundary**
   - Should interpolation live in `tpt-css`, `tpt-layout`, or a separate animation crate?

8. **CSSOM serialization**
   - How much round-trip fidelity is required for M3?

9. **UA stylesheet**
   - Should the Web UA stylesheet live in `tpt-css`, `tpt-dom`, or `tpt-html`?

10. **Strict license interpretation**
    - Resolved: first-party code is dual `MIT OR Apache-2.0`.
    - Still open: dependency policy. The default is no third-party core dependencies.
    - Resolved: no Apache-only dependencies. Every allowed dependency must offer MIT.
